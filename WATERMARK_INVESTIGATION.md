# Statistical Watermark Investigation — foldrise

**Status: NO EVIDENCE**

This is not the same as "watermark does not exist." It means: across every test that can be run without the watermark's secret key, no signal was found, and the corpus is additionally too small/fragmented for word-choice statistics to be conclusive even in principle. See "What would actually settle this" at the end.

## 2. Methodology

Two investigation phases, run in this order:

**Phase A — Structural forensics** (completed earlier this session): Unicode/invisible-character scan, encoding-function search (`atob`/`btoa`/`fromCharCode`/etc.), whitespace/indentation bit-channel tests (5 separate stylistic-encoding hypotheses), numeric-literal distribution analysis, PNG metadata-chunk extraction, JPEG EXIF extraction, `.webm`/`.DS_Store` string scans, and near-duplicate-file differential analysis (8 structurally identical page templates diffed against each other).

**Phase B — Lexical/word-choice analysis** (this pass): extracted every code comment containing 5+ words, separated genuine prose from commented-out code fragments, and computed descriptive statistics on the resulting corpus.

## 3. Corpus measurement

The requested mechanism (word-choice bias) can only leave a signal in free natural-language text — not in code syntax, JSX, config values, or file names. So the first question is: how much actual prose exists in this repo?

| Source | Words | Assessment |
|---|---|---|
| `README.md` | 155 | Stock `create-next-app` boilerplate, not project-specific writing |
| `AGENTS.md` | 95 | Auto-generated by the Next.js dev server itself (file states this) |
| `CLAUDE.md` | 1 | Single `@AGENTS.md` import line |
| `buddyGuide.txt` | 258 | Author's own Roman Urdu dev notes |
| `TEXT.txt` | 529 | Pasted JSX/code fragments, not prose |
| **Code comments (all 193 comment blocks)** | **1,548 raw words** | Mixed — see below |

Of the 193 total comment blocks, only **111** contain 5+ words (i.e., could plausibly be a sentence rather than a label). Of those 111, **6 were commented-out code** (JSX/attribute fragments like `onChange={handleFileChange} className="hidden"`) and excluded. That leaves:

**105 genuine prose comments, totaling 1,230 words, spread across 20 files.**

This is the entire candidate corpus for word-choice-bias detection in this project.

## 4. Lexical descriptive statistics

Computed on the 1,230-word prose corpus (script: `lexical_analysis.py`, rerunnable):

- **Type-token ratio: 0.398** (490 unique word forms / 1,230 total words)
- **Hapax legomena: 272 words (55.5% of all unique types) occur exactly once** — a corpus this sparse gives almost no repeated-word statistics to test bias on
- **Function-word rates** deviate from generic English baselines in both directions (e.g. "so" appears at 19.5/1000 vs. a ~3/1000 baseline; "of" at 13.8/1000 vs. ~32/1000 baseline) — expected for technical/explanatory comment writing, not itself evidence of anything
- **Synonym-pair counts**: overwhelmingly one-sided (e.g. `so`=24 vs `therefore`=0; `keep`=2 vs `maintain`=0; `use`=0 and `utilize`=0). This pattern — plain/short word almost always chosen over its formal synonym — is the normal register of terse code comments, not a statistical anomaly; formal synonyms are essentially never natural in this context regardless of who/what wrote it.
- **Em-dash usage**: 28 instances of `—` vs. 8 of `--`. Consistent within-file, suggests a single author/style convention, not a marker.
- **Per-file TTR** ranges narrowly (0.646–0.915) with no discontinuity between files — no evidence of a uniform hidden signal that would need to look identical file-to-file.

**None of these numbers are being presented as evidence of a watermark.** A corpus this size cannot produce statistically significant word-bias claims for any individual pattern — that itself is the finding (see §5).

## 5. Why this corpus cannot resolve the question, even in principle

Two independent, non-opinion reasons:

1. **No detector key.** The described mechanism (hidden score biasing synonym choice) is only checkable by whoever holds the secret seed used to bias the choices. Without it, "the author picked this word" and "the algorithm favored this word" are indistinguishable — that's what makes it a *secret* watermark, not a flaw in this investigation's effort.

2. **Corpus is structurally too small and fragmented.** 1,230 words split across **105 disconnected snippets averaging ~12 words each**, in a technical-comment register with limited true synonym freedom (there's no natural alternative word for `pathname`, `zoom stop`, or `sidebar`). Published word-choice watermarking research generally relies on long, contiguous generated passages precisely because short/fragmented text doesn't carry enough independent word-choice decisions to distinguish signal from noise. This repo's comments don't meet that bar structurally, regardless of what threshold number you'd cite — the largest single contiguous comment is 55 words.

*(An earlier draft of this analysis computed a specific detection z-score under an assumed bias strength. That number is not included here — it depended on a bias-magnitude parameter this investigation has no way to verify, and presenting a precise-looking statistic built on an invented parameter would be exactly the kind of manufactured evidence this report is committed to avoiding.)*

## 6. Anomalies found (from Phase A) and their explanations

| Anomaly | Location | Explanation |
|---|---|---|
| 2× non-breaking space (U+00A0) | `app/components/sidebar.tsx:99-100` | Leading whitespace before SVG tags — classic paste-from-design-tool artifact |
| 40 lines with trailing whitespace | 11 files | Plain spaces only, no tab/space bit-pattern, correlates with indentation depth — editor noise |
| Uniform `Software=Figma` tEXt chunk | All 7 PNGs | Standard Figma export metadata, identical in every file (zero information capacity as a channel) |
| Uniform double-quote preference | Nearly all files | Prettier/ESLint-enforced style, not a per-file variable signal |

No base64/hex/binary-encoded payloads, no BOM, no zero-width Unicode, no `eval`/`atob`/`fromCharCode` usage anywhere in the codebase.

## 7. What was NOT tested, and why

- **Pixel-level LSB steganography on the 7 PNGs/webm** — without an expected payload or key, this is unbounded noise-fishing; any "pattern" found this way would be a guaranteed false positive.
- **Brute-force encoding search until something readable appears** — same problem; this method finds "hits" in random data by construction and was explicitly excluded from this investigation's methodology from the start.

## 8. What would actually settle this

Two paths, both outside what this repo can prove on its own:

1. **Ask the developer who built the watermark for their detector/key.** If it was genuinely applied, they must have a way to verify it — a watermark that even its own creator can't check is unfalsifiable and not useful as a compliance tool anyway.
2. **If the concern is Claude/Anthropic specifically**, check Anthropic's official documentation or support channel for whether a public detector exists. No third-party inspection (including this one) can confirm or rule out a key-based scheme from the outside.

If the original pre-paste text (before it entered this repo) can be located, a direct before/after character diff against what's now in the files would be a genuinely new, testable lead — offer still stands.
